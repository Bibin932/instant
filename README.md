# Self-hosted Meta Lead Ads → Existing CRM bridge

This Node.js service receives Meta Page `leadgen` webhooks, fetches the full lead from the Meta Graph API, converts the form answers into the exact JSON shape supplied for your existing CRM, and sends the lead to that CRM API.

It does **not** require access to the existing CRM's source code. It uses the CRM's existing HTTP API.

## Your CRM integration details already configured

- CRM API URL: `https://likv34svlb.execute-api.ap-south-1.amazonaws.com/prod/create-online-leads`
- JSON wrapper: `{ "tableName": "...", "data": [ ...one lead... ] }`
- Table: `OnlineLeads-qr2mdczhwfhc7nmmkiafsfjlui-prod`
- CRM record properties (spellings preserved): `firstName`, `lastName`, `email`, `phone`, `interestedCourse`, `remarks`, `assignedTo`, `campainName`, `waNumber`, `formType`, `preferedLanguage`, `hideLead`
- `assignedTo` defaults to the UUID from the supplied sample. Change `CRM_ASSIGNED_TO` if another owner should receive Meta leads.
- `formType` defaults to `LANGUAGE`; `preferedLanguage` defaults to `English`; `hideLead` defaults to `false`.
- Each Meta webhook creates one request to the CRM with one item in the `data` array. This matches the supplied request structure.

## Requirements

- Node.js 20 or later
- A public domain/subdomain with HTTPS, pointed to this service through a reverse proxy
- A Meta Developer App with Webhooks and Lead Ads permissions configured
- A CRM API key and the **same auth header format used by your successful Postman request**

## Install on Hostinger VPS / aaPanel

1. Upload and extract this folder, for example to `/www/wwwroot/leadsync.yourdomain.com`.
2. In that directory, run:

   ```bash
   npm install
   npm run setup
   ```

   `npm run setup` creates `.env`, a random Meta webhook Verify Token, and a random admin password. Save the printed admin password and Verify Token. The generated `.env` file is private and is excluded from the ZIP.

3. Edit `.env` and fill in:
   - `PUBLIC_BASE_URL=https://leadsync.yourdomain.com`
   - `META_APP_SECRET` from Meta App Settings → Basic → App Secret
   - `META_PAGE_ACCESS_TOKEN` for the Page whose forms you are syncing
   - `CRM_API_KEY` with your existing CRM API key
   - `CRM_AUTH_HEADER` and `CRM_AUTH_PREFIX` to match the working Postman request exactly

4. Start the server:

   ```bash
   npm start
   ```

5. Confirm the health endpoint:

   `https://leadsync.yourdomain.com/health`

   It should return `{"ok":true,...}`.

6. Keep it running with PM2:

   ```bash
   npm install -g pm2
   pm2 start server.js --name meta-crm-bridge
   pm2 save
   pm2 startup
   ```

   Follow the one command PM2 prints after `pm2 startup`, then run `pm2 save` again.

7. Configure aaPanel Nginx reverse proxy from `leadsync.yourdomain.com` to `http://127.0.0.1:3000`, and issue SSL. Do not expose port 3000 directly if you can use the HTTPS reverse proxy.

## Environment variable guide

| Variable | What to enter |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `3000` (or the private port you use) |
| `PUBLIC_BASE_URL` | Your public HTTPS base URL, without a trailing slash |
| `META_APP_SECRET` | Meta App Secret (server secret) |
| `META_VERIFY_TOKEN` | Generated by `npm run setup`; use the same value in Meta webhook configuration |
| `META_GRAPH_VERSION` | `v27.0` (current Graph API release on 10 Nov 2026; check Meta's versions page before future upgrades) |
| `META_PAGE_ACCESS_TOKEN` | Page Access Token for one Page |
| `META_PAGE_TOKENS_JSON` | Optional JSON map of Page IDs to Page tokens if several Pages use the same bridge |
| `CRM_API_URL` | Already set to the endpoint you supplied |
| `CRM_API_KEY` | Your existing CRM API key |
| `CRM_AUTH_HEADER` | Exact header name from Postman; `x-api-key` is the AWS API Gateway convention, but verify your working Postman request |
| `CRM_AUTH_PREFIX` | Blank for `x-api-key: key`; use `Bearer` for `Authorization: Bearer key` |
| `CRM_EXTRA_HEADERS_JSON` | Optional JSON object of additional required headers |
| `CRM_TABLE_NAME` | Already set to your supplied table name |
| `CRM_ASSIGNED_TO` | Already set to the owner UUID from your sample; replace if needed |
| `CRM_CAMPAIGN_NAME_DEFAULT` | Fallback campaign name if Meta ad campaign details cannot be read |
| `CRM_FORM_TYPE` | `LANGUAGE` per your example |
| `CRM_PREFERRED_LANGUAGE` | `English` per your example |
| `CRM_HIDE_LEAD` | `false` per your example |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Dashboard HTTP Basic Auth; generated admin password is printed by setup |

### Important: confirm the Postman authorization header

The API URL and request body do not tell us how the API key is sent. Look in your successful Postman request under **Headers** or **Authorization**:

- If it shows `x-api-key: <key>`, keep `CRM_AUTH_HEADER=x-api-key` and `CRM_AUTH_PREFIX=`.
- If it shows `Authorization: Bearer <key>`, set `CRM_AUTH_HEADER=Authorization` and `CRM_AUTH_PREFIX=Bearer`.
- If it uses a different header (for example `api-key`), put that exact name in `CRM_AUTH_HEADER`.

Do not paste the real key into source code or share it in screenshots. Store it only in `.env` on the server.

## Meta Developer setup

1. In Meta for Developers, select your app and add/configure **Webhooks**.
2. Subscribe the app to the **Page** object and the `leadgen` field.
3. Set Callback URL to:

   `https://leadsync.yourdomain.com/webhooks/meta`

4. Enter the exact `META_VERIFY_TOKEN` from `.env` as the Verify Token.
5. Complete verification. Meta sends a GET request; this service validates the token and returns the challenge.
6. Subscribe the app to the Facebook Page's leadgen events. A Page subscription is also required; configure it via Meta's Page subscription flow/Graph API.
7. Ensure the app/Page has the required Lead Ads permissions and Page lead access, including `leads_retrieval` and the relevant Page permissions. Meta may require App Review / Advanced Access for production use and for Pages outside app-role access.
8. Run a test lead using Meta's Lead Ads Testing Tool.

The service validates the `X-Hub-Signature-256` HMAC using `META_APP_SECRET`, stores the webhook in a local queue, returns HTTP 200, and processes the queued lead asynchronously.

## Field mapping behaviour

The service reads Meta `field_data` and matches common field labels, including full name, first/last name, email, phone, WhatsApp, course, remarks/specialization and language. Meta form field labels can be different from one form to another.

- If Meta sends a `full_name` field, it is copied into both `firstName` and `lastName` by default, matching the sample JSON you supplied. If Meta sends separate first and last names, those values are used separately.
- `phone` and `waNumber` use the detected phone/WhatsApp field.
- `interestedCourse` and `remarks` use common course/program/specialization aliases. You can override aliases using `META_FIELD_ALIASES_JSON`.
- `campainName` is populated by looking up the ad's campaign name through the Graph API. This can require additional Meta permissions. If the lookup fails, `CRM_CAMPAIGN_NAME_DEFAULT` is sent.
- `assignedTo`, `formType`, `preferedLanguage`, and `hideLead` use the configured defaults above.

Example override (field names on the left are CRM mapping keys):

```env
META_FIELD_ALIASES_JSON={"interestedCourse":["Which course are you interested in?","Course category"],"remarks":["Specific program","Specialization"]}
```

Keep this as valid JSON on a single line.

## Dashboard and monitoring

- Root URL `https://leadsync.yourdomain.com/` redirects to the dashboard.
- Dashboard: `https://leadsync.yourdomain.com/admin`
- Login: HTTP Basic Auth using `ADMIN_USERNAME` and `ADMIN_PASSWORD`
- Health: `https://leadsync.yourdomain.com/health`
- Dashboard shows received, synced, pending and failed jobs, recent lead IDs, and retry controls.
- The local queue is stored in `data/state.json` and retained for `JOB_RETENTION_DAYS`.
- Failed events retry automatically with exponential backoff. You can manually retry failed jobs from the dashboard.

Back up `data/state.json` if you need to preserve the integration's local delivery history. Restrict filesystem permissions on `.env` and `data/`.

## Test flow

1. Verify `/health` works over HTTPS.
2. Check `https://leadsync.yourdomain.com/admin` and log in.
3. Open the dashboard's configuration summary. Fill any missing settings in `.env` and restart the service.
4. Configure the Meta webhook and Page subscription.
5. Submit a Meta test lead.
6. Watch the dashboard. A lead should move from `queued` / `processing` to `synced` after the CRM returns a 2xx response.
7. Check the live CRM dashboard for the new record.

## Operational caveats

- **This project has not called your live CRM API.** No real API key was provided, and the auth header is not identifiable from the endpoint and body alone. Use the same header that works in Postman.
- A successful HTTP 2xx response is treated as accepted by the CRM. Confirm a test lead appears in the CRM before enabling ads broadly.
- Local deduplication prevents repeated Meta webhook events from being sent again after a lead is recorded. If the CRM creates a record but the network times out before its response reaches this service, a retry could still create a duplicate unless the CRM itself supports an idempotency key or duplicate checking. Ask the CRM team whether it deduplicates by phone or supports a client-supplied unique ID.
- Ad campaign lookup may fall back to `CRM_CAMPAIGN_NAME_DEFAULT` if Meta does not grant the token access to the ad/campaign object. Add the required Meta Ads read permission where appropriate, or use a fixed campaign label.
- This bridge sends one CRM request per lead, with one object in the `data` array, matching your sample's outer schema. The original sample showed two records in one request; this integration uses one record per event for immediate delivery.
- No Make.com, Zapier or other paid automation platform is used. Your VPS, domain/SSL and Meta access requirements still apply.

## Security checklist

- Never commit `.env` to GitHub.
- Keep App Secret, Page Access Token and CRM API key only on the server.
- Use HTTPS for the Meta callback.
- Use a strong admin password; the setup script generates one.
- Restrict access to `/admin` via the generated Basic Auth credentials and optionally an IP allowlist in Nginx.
- Do not expose the `data/` directory through the web server.
